## Key Root Causes Fixed

### 1. ARM64 pointer truncation

Original N64 code stored pointers in s32/u32 fields.
On ARM64 this truncates 64-bit host pointers, causing crashes.

Fixed:
- Mesh transform callback prototypes in src/core2/code_C5440.c now use BKModel* instead of s32
- func_802F32C4 caller in src/core2/ch/bubble.c now passes void* instead of s32
- Several BKA_TRANSLATE_ADDR guards added

### 2. Heap allocation size mismatch

Original N64 Struct_core2_6B030_0 contains two 4-byte pointers = 8 bytes.
On ARM64 two pointers = 16 bytes.

Fixed:
- D_80368AB0 = malloc(2 * sizeof(Struct_core2_6B030_0))

Location: src/core2/code_6B030.c

### 3. Software RDP Gfx stride

Gfx command union is 8 bytes in N64 headers, but the Android build's Gfx
alignment has caused stride confusion.

Current GfxCommand remains 16 bytes due to observed top-level alignment.
If nested DL parsing becomes corrupted, revisit stride.

### 4. Endianness of model/geo data

N64 assets are big-endian. Host is little-endian.

Fixed:
- modelbin_get*_MACRO offsets use byteswaps
- modelRender_geoCmd_bswap handles subfields for F3DEX_GBI geo commands
- meshList_getMesh / meshList_getVtxCount use bswap16 where necessary

Location: include/model.h, src/core2/modelRender.c, src/core2/code_62FD0.c

### 5. F3DEX_GBI opcode mapping

The game uses F3DEX_GBI, not F3DEX_GBI_2.
Initial software RDP switch was wrong.

Correct mapping:
- 0x01 = G_MTX
- 0x04 = G_VTX
- 0x06 = G_DL
- 0x03 = G_MOVEMEM
- 0xBF = G_TRI1 (raw RDP/immediate variant used by game)
- 0xB1 = G_TRI2 (raw RDP/immediate variant used by game)
- 0xBC = G_MOVEWORD
- 0xB8 = G_ENDDL
- 0xBD = G_POPMTX
- Many raw RDP opcodes unchanged

Location: Android/app/src/main/cpp/emulator/gfx_interpreter.cpp

### 6. RDP host-pointer address translation

Raw GBI commands sometimes contain low-32 ARM64 host pointers.
RDP_TranslateAddr checks bka_lookup_addr_mapping first,
then N64 physical/KSEG0/KSEG1, then reconstructs 0x7c... host pointer.

Remaining issue: segment-relative addresses from G_MOVEWORD are not resolved.

## Current Biggest Blocker

### RSP segment translation and nested display-list parsing

The top-level display list is parsed correctly, but when G_DL jumps to a
nested display list, the address may be segment-relative or may point to
non-command data. This causes:

- RDP_TranslateAddr reconstructing incorrect host pointers
- Many Unhandled op=0x... warnings
- No visible geometry yet

Observed problem commands:
- 0xBC G_MOVEWORD segment setup is currently ignored
- 0x06 G_DL uses raw address without segment resolution
- Nested display list sometimes starts with non-command bytes

Next actions:
1. Implement uint32_t segmentBase[16] in RDPState
2. Implement G_MOVEWORD (0xBC) for G_MW_SEGMENT
3. Resolve G_DL/G_VTX addresses using segment base before fallback
4. Add more RDP command handlers (0xF9, 0x15, 0x41/0x42/0x43, etc.)
